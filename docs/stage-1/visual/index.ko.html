Calibration Report Trustworthiness

왜

주간 보정 리포트는 운용자 의사결정의 근거가 되지만, 두 가지 구조적 결함으로 인해 조언이 오해를 불러일으킬 수 있었다. 첫째, 보정 버킷과 신호 성과 테이블이 선택된 시간 창과 무관하게 항상 전체 예측 이력을 기준으로 계산됐다. "7일 창" 섹션에서도 전체 기간 데이터(예: technical n=445)가 표시돼, 최근 모멘텀 개편 이후 신호가 회복됐다는 사실(7일 technical ~52% vs. 전체 ~38%)이 숨겨졌다. 둘째, 버킷이 항상 원시 confidence를 기준으로 계산돼, 라이브 isotonic 재보정기가 과신 격차를 줄이고 있는지 리포트가 보여줄 수 없었다. 게다가 "confidence를 깎아라"라는 권고는 재보정기를 이중으로 교정하는 결과를 낳을 수 있었다 — 재보정기는 이미 원시 0.61을 재보정 행 기준 약 0.31로 매핑하고 있었기 때문이다.

무엇을
  • get_calibration_report와 get_signal_performance에 outcome_date 기준 선택적 days 창 필터 추가 — 기존 get_track_record 의미론과 일치.
  • get_calibration_report에 use_raw 파라미터 추가 (기본값 True = 원시 confidence, 재보정 훈련 경로 보존; False = 로그 기록값/재보정 후 confidence).
  • 두 값이 차이날 경우 창마다 두 개의 보정 테이블(원시 vs. 로그 기록값)을 렌더링하고, 일치할 경우 하나의 테이블과 설명 노트로 축약.
  • 헤드라인 과신 경고는 이제 로그 기록 곡선 기준; 원시 플래그는 추세 파일 플로팅용으로 overconfident_buckets_raw에 유지.
  • 라이브 결과: 7일 창에서 원시 드리프트 +0.09 vs. 로그 기록 +0.02 — 재보정기가 최근 데이터에서 격차를 좁히고 있음을 확인.
어떻게

테스트 우선(TDD): 먼저 7개의 실패 테스트(test_metrics.py 4개, test_weekly_calibration.py 3개)를 작성하고 최소한의 코드로 통과시켰다. 창 처리는 get_track_record가 이미 사용하는 outcome_date >= datetime('now', ?) 술어를 그대로 재사용해 모든 창 섹션이 헤드라인 숫자와 정렬되도록 했다. 두 번째 테이블 도입으로 생길 중복을 방지하기 위해 _render_bucket_table 헬퍼를 추출했다. Codex 리뷰에서 ISO 문자열 사전순 비교가 동일 마감일의 이전 시각 행을 잘못 포함하는 버그를 발견했고, 신규 쿼리와 공유 _closed_filter 헬퍼 모두에 datetime(outcome_date) 래핑으로 수정했다.

Candidate Discovery

왜

2026-05-13 cron 일일 브리핑이 "피지컬 AI" 테마 폭등(현대오토에버 +55%, LG전자 +34%, 현대차 +30% / 10일)을 완전히 놓치고 Samsung / SK하이닉스 / 현대차만 재추천했다. 근본 원인: scheduler/daily_briefing.py가 KR 블루칩 6종목을 하드코딩해 mid-cap 모멘텀 종목이 LLM 시야 밖에 있었다. 브리핑 스킬의 프레이밍이 LLM을 앵커링하는 두 번째 원인은 2단계에서 다룬다. 1단계는 하드코딩된 유니버스를 제거한다.

무엇을

  • 하드코딩 6종목을 3개 reference 앵커로 축소: 삼성전자(005930), SK하이닉스(000660), KODEX 200(069500).
  • scheduler/daily_briefing.py: API 모드용 fetch_kr_market_data() 재작성; KR Claude Code cron 프롬프트에 {candidate_block}과 {ticker_csv} 동적 주입.

어떻게

  • 뉴스 카운트는 2단계로 연기: 200종목 뉴스 fetch는 timeout 위험 → theme clusterer가 상위 30개 후보에만 backfill.

  • 종목명 조회는 필터 통과 생존자(~20–30종목)에만 적용해 PyKRX 순차 호출 횟수 절감.
  • discover_kr_candidates(provider=...)로 단위 테스트에서 fake provider 주입 가능.

Tier1 Signal Gate Recal

왜

측정된 핵심 결함 3종을 직격했다: (S1) valuation/cycle/mean_reversion 신호 유형의 승률 0%, 프루닝 메커니즘 없음; (S2) LIVE 예측의 39%가 저품질이고 BEAR 방향이 충분한 게이트 없이 6% 비율로 발행됨; (S3) confidence 값이 ~0.60 상수에 고착 — 정보 없음. 설계는 Vibe-Trading(MIT) 신호 IC/분류·재보정 철학과 AutoHedge 리스크-퍼스트 게이트 아이디어에서 착안했다.

무엇을
  • S1: get_signal_performance에 신호 유형별 이항검정 양측 p-value와 verdict(alive / weak / dead) 추가. 실데이터에서 valuation/cycle/mean_reversion이 정확히 dead(p=0.001)로 식별됨; 나머지는 weak.
  • S2: /expect 및 daily-briefing 프롬프트에 리스크/엣지 게이트(reward:risk < 1.5 등록 금지) 및 BEAR 상향 바(신호 ≥3개 + 매크로 확인 + RR ≥ 2.0; LIVE는 NEUTRAL 강등) 추가.
  • S3: 단조 재보정 맵(isotonic regression / PAVA) 적합 및 적용. 실데이터: 원시 0.626 → 0.50으로 과신 교정. CLI calibration 서브커맨드 출력에 재보정 맵 노출.
어떻게
  • _binomial_two_sided_p는 math.comb만 사용해 외부 의존성 없음; 이후 n ≳ 1100에서 overflow 방지를 위해 로그-감마 공간으로 재작성(Codex PR 리뷰 #27에서 발견).
  • _signal_verdict가 get_signal_performance에 하위 호환 신규 필드로 추가됨 — 기존 consumer 4개 무수정.
  • _isotonic_nondecreasing(PAVA) → build_recalibration_map / apply_recalibration(선형 보간; 빈 맵은 항등 함수).
  • TDD: 신규 테스트 9개(verdict ×3, recalibration ×3, weekly ×1, 기존 보강 ×2). 전체 not network 스위트: 287개 통과.

Toss Open Api

왜

portfolio sync가 비공식 tossctl CLI에 의존했다 — 브라우저/QR 로그인이 필요하고, 약 주 1회 세션이 만료되며, 세션 만료 모니터와 Telegram 알림이 별도로 필요했다. 토스증권이 이제 공식 Open API(OAuth2, REST/JSON)를 제공하므로, 서버 사이드 자격증명과 자동 토큰 갱신으로 브라우저 세션 관리를 완전히 대체할 수 있다.

무엇을
  • 신규 portfolio/toss_api.py: OAuth2 client-credentials 클라이언트 — 토큰 발급/캐시, 계좌 목록 조회, 보유 종목 조회, reconcile()이 이미 소비하는 딕셔너리 형태로 각 보유 종목 정규화.
  • portfolio sync는 공식 API를 우선 사용하고, 자격증명이 없으면 tossctl로 fallback. 신규 --source {auto,toss-api,tossctl} 플래그; 출력 JSON에 실제 사용된 source 기록.
  • 불필요해진 세션 만료 모니터 제거: scheduler/toss_auth_check.py, 해당 테스트, 07:30 cron 라인, 문서 참조 전체.
  • .env 경유 자격증명: TOSS_CLIENT_ID, TOSS_CLIENT_SECRET (선택적 TOSS_OPENAPI_BASE_URL).
  • 라이브 검증 완료: 토큰 발급, BROKERAGE 계좌, 18개 보유 종목(KR 6개 + US 12개)을 portfolio sync --source toss-api --dry-run으로 정상 동기화 확인.
어떻게

조정(reconciliation) 로직, DB 스키마, ticker/시장 정규화는 데이터 소스에 무관하게 설계돼 있어 전혀 수정하지 않았다. 신규 코드는 경계부에만 위치한다: toss_api.fetch_toss_positions_api()가 tossctl이 반환하던 것과 동일한 정규화된 포지션을 생성하므로 toss_sync.reconcile()은 불변. 얇은 디스패처 toss_sync.fetch_positions(source)가 소스를 선택한다. 엔드포인트는 https://openapi.tossinvest.com/openapi-docs/latest/openapi.json의 정식 스펙으로 확인 — 초기 가정(인증 방식, 경로 prefix, accountSeq 헤더)이 모두 틀렸고 구현 전에 수정했다.
