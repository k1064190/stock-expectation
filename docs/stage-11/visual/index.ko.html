11단계

예측 정확도 개선 이니셔티브: 읽기 전용 백필 A/B 평가 게이트 구축과 함께, 결정론적 신뢰도 재보정 및 죽은 시그널 정리를 통해 낙관 편향이 라이브 /expect 흐름으로 유입되는 것을 방지합니다.

Backfill Harness

왜

예측 적중률이 73%(2026-05-11)에서 24%(2026-06-14)로 붕괴했습니다. 승인된 계획은 여섯 가지 정확도 변경(A-F)을 규정하고 있으며, 각 변경 사항은 라이브 /expect 흐름에 적용되기 전에 반드시 과거 데이터로 검증되어야 합니다 — 그렇지 않으면 LIVE-vs-INTERACTIVE 낙관 편향(F4)이 반복될 위험이 있습니다. 이 하네스가 바로 그 게이트입니다.

무엇을

scheduler/backfill_eval.py — 종료된(HIT/MISS) 예측을 대상으로 하는 읽기 전용 A/B 도구이며, tests/test_backfill_eval.py (9개 테스트, 전체 통과)가 포함됩니다.

보고서에 포함되는 항목:

  • [A] 등온 재보정 — 누설 방지: 이전 학습 슬라이스로 재보정 맵을 피팅하고, 보류된 최근 테스트 슬라이스에서 원시 대 재보정 Brier 점수를 산출합니다.
  • [B] 죽은 시그널 기여도 — 종료 행을 죽은 시그널 (valuation/cycle/mean_reversion) 사용 여부로 분류합니다.
  • [D] 레짐 구간 억제 — 리스크-오프 구간 내에 생성된 BULL 예측의 결과 (강경 레짐 게이트가 적용되었을 경우 억제되었을 예측)를 분석합니다.
첫 실행 결과 (실제 DB, n=420 종료)
변경 지표 이전 이후
A (recal, OOS) ALL Brier 0.340 0.204
A (recal, OOS) LIVE Brier 0.331 0.160
B with-dead-signal 적중률 — 0.0% (n=15, Brier 0.424)
D BULL 6/1-6/7 적중률 — 4.3% (n=140)

이 결과는 A와 D를 강하게 검증하고, B는 노이즈(소량)임을 확인합니다.

어떻게

재구현 대신 프로덕션 보정 수학(build_recalibration_map, apply_recalibration, get_calibration_report — mcp-prediction-store/metrics.py)을 재사용합니다. 학습 슬라이스는 인메모리 DB에 로드되어 버킷팅이 라이브와 동일하게 유지됩니다. 시간 순 분할은 get_signal_decay (outcome_date, created_at, id)를 따릅니다.

기존 알려진 문제

회고

인메모리 DB를 통해 프로덕션 재보정 빌더를 재사용함으로써 하네스의 정직성을 유지했습니다 — 라이브와 달라질 수 있는 중복 보정 로직이 없었습니다. 세 검토자 루프는 충분한 가치를 발휘했습니다: codex가 읽기 전용 계약 위반과 데이터를 잘못 탓하게 한 서식 버그를 잡아냈습니다. 교훈: 데이터를 탓하기 전에 표시 경로를 먼저 검증하세요.

Recalibration And Dead Signals

왜
  • F1/F7 (과잉 확신 + 미사용 재보정 맵): 0.60-0.70 신뢰도 구간이 실제 대비 +0.28 과도하게 높았으며, /expect가 운영자에게 수동으로 재보정 맵을 적용하도록 안내했음에도 백필 결과 기록된 신뢰도가 여전히 ~0.6에 가까웠습니다. 수동 LLM 단계는 신뢰할 수 없으므로 재보정은 결정론적이어야 합니다.
  • F2/F5 (죽은 시그널): valuation, cycle, mean_reversion이 0%를 기록하며 시그널별 보정만 오염시킵니다.
무엇을
  • A — predict create에 --recalibrate 플래그 추가 (stock_cli.py). 저장 전 원시 --confidence를 소스 범위 등온 곡선에 통과시키며, JSON에 raw_confidence / recalibration_applied를 출력합니다. 해당 소스의 종료 예측이 MIN_CLOSED_FOR_RECAL = 30 미만일 경우 안전하게 무작동(no-op)합니다.
  • B — 죽은 시그널 제거 — /expect와 daily-briefing 스킬 모두의 허용 --signals 목록에서 제거했습니다. 운영자는 해당 읽기를 LLM_CONTEXT_SCORE로 라우팅하도록 안내받습니다.
  • 기존 수정 (승인됨): weekly_calibration.py:208,236이 avg_return에 :+.2%(100배 팽창)를 사용했습니다. :+.2f%로 수정.
  • 테스트: tests/test_recalibration_cli.py (3개) — 최소 샘플 게이트, 과잉 확신 감소, 소스 범위 지정.
어떻게

재보정은 build_recalibration_map/apply_recalibration (mcp-prediction-store/metrics.py)을 재사용합니다. 전역(전체 수평선) 맵을 사용합니다 — 백필 결과 수평선별 맵과 동등한 정확도를 보였으며(Brier 0.160 vs 0.169), 현재 샘플 크기에서 더 견고합니다. 소스 범위 지정: LIVE 예측은 LIVE 히스토리에만 대조하여 보정하며, 과적합된 INTERACTIVE 행은 사용하지 않습니다(F4 격차). 로깅 임계값은 여전히 원시 신뢰도 기준으로 판단하고, 저장되는 값만 재보정되므로 "각 수평선 >= 0.60 저장" 의미론은 변경되지 않습니다.

검증

백필 OOS Brier: LIVE 0.331 에서 0.160, ALL 0.340 에서 0.204 (누설 방지 학습/테스트 분할).

라이브 맵 검사에서 드러난 주의사항: 프로덕션 LIVE 곡선은 원시 신뢰도가 거의 일정하기 때문에 단일 앵커(0.612 에서 0.248)만 가지고 있어, 재보정이 모든 신뢰도를 ~0.25 기저율로 수렴시킵니다. 이것이 Brier 향상의 원인이지만(기저율이 비정보적인 0.6을 이기는 것 — 순열 테스트에서 원시 신뢰도가 신호를 전달하지 않음이 이미 확인됨), 모델이 정보적인 신뢰도 분포를 생성할 때까지 기록된 신뢰도가 종목 순위 지정을 멈춘다는 의미입니다. 식별 능력 회복은 하위 작업(변경 E / 메타 레이블링)이며 재보정의 역할이 아닙니다.

리뷰 루프
  • CRITICAL (전원, 수정) — 재보정이 자체 학습 데이터를 오염: 재보정된 값을 confidence에 다시 저장하면 향후 맵이 오염됩니다 (build_recalibration_map/get_calibration_report는 confidence를 원시 예측자로 읽기 때문에, 재보정된 행이 원시인 것처럼 곡선에 재진입해 도메인을 붕괴시키고 재실행 시 이중 적용). 수정: nullable raw_confidence 컬럼 추가 (models.py 스키마 + _ensure_raw_confidence_column 마이그레이션 + dataclass/insert/reader); 보정은 COALESCE(raw_confidence, confidence)로 학습하여 재보정된 값을 절대 볼 수 없습니다. 새 테스트 test_map_trains_on_raw_not_recalibrated가 저장값 0.30/원시값 0.65 행이 0.65를 맵에 기여함을 증명합니다. 프로덕션 복사본에서 마이그레이션 검증 완료(1169행 보존, 컬럼 추가, 레거시 맵 변경 없음).
  • 수정 — 테스트 부족 (codex/code-reviewer): 게이트 후 빈 맵 무작동 테스트, 비오염 테스트, 원시값 보존 및 저장 신뢰도 보정을 검증하는 종단간 cmd_predict_create --recalibrate 테스트를 추가했습니다.
  • 인지됨 — 재실행 이중 적용: 호출자가 저장된(이미 보정된) 신뢰도를 --recalibrate로 수동 재제출하면 다시 맵핑됩니다. 정상적인 /expect 경로(항상 모델의 원시 신뢰도를 전달)에서는 발생하지 않습니다. 문서화했으며 게이트는 추가하지 않았습니다.

회고

재보정을 수동 LLM 지침에서 CLI 플래그로 전환한 것이 F7의 실질적 해결책입니다 — 맵은 몇 주 동안 존재했지만 신뢰성 있게 적용된 적이 없었습니다. 백필 델타만이 아닌 실제 라이브 맵을 직접 검사함으로써 재보정이 현재 기저율로 수렴한다는 사실을 발견했습니다. 나중에 신뢰도가 식별 능력을 잃었다는 것을 발견하는 것보다, 지금 솔직하게 기록해두는 편이 낫습니다.
