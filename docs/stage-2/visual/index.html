Bear Sign Gate Dedup

Why

A full audit of 920 rows surfaced structural bugs and data corruption: an outcome_return sign bug (BEAR HITs recorded as negative, MISSes as positive) poisoned every return metric; LIVE BEAR predictions continued to be generated despite a 0% win-rate; up to 18 duplicate rows per ticker per day; and analysis_group_id remained unused.

What
  • 2.1 BEAR sign: outcome_return redefined as position return (BEAR = −price_change). BULL and NEUTRAL unchanged.
  • 2.2 Store gate: insert_prediction now rejects LIVE + BEAR combinations and rejects duplicate rows sharing the same 6-key tuple. A partial UNIQUE index serves as the concurrency backstop.
  • 2.3 group_id: daily-briefing prompt updated with per-ticker --analysis-group-id guidance.
  • 2.4 Backfill: one-shot migration reverses historical BEAR signs and removes same-6-key duplicates. Runs after a verified backup.
How

evaluate_prediction: signed = -pct_change if BEAR else pct_change. Duplicate key = (ticker, market, direction, timeframe, source, date(created_at)) — identical across the live guard, migration, and UNIQUE index; entry_price deliberately excluded. Migration uses an atomic BEGIN/rollback transaction, a _migrations marker to block re-runs, and SQLite Connection.backup() for a WAL-consistent backup before execution. TDD: full not-network suite at 293 passing. Real DB: 920 → 732 rows (188 duplicates removed), 38 BEAR sign corrections applied.

Retrospective

The key mismatch was caught during review — all three enforcement points (live guard, migration, UNIQUE index) had to converge on a single key definition for deduplication to be consistent. The backfill is irreversible, so the safe sequence was: backup, verify restore, then apply. The BEAR LIVE store gate and the prompt BEAR bar form a layered defense.
